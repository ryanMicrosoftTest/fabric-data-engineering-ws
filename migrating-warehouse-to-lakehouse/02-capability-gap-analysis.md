# 02 — Capability Gap Analysis

This is the detailed list of what changes when a workload moves from a Fabric Warehouse
to a Fabric Lakehouse. Work through it object type by object type against the output of
[`assessment/warehouse_inventory.sql`](assessment/warehouse_inventory.sql).

Severity key:

- 🔴 **Blocker** — no direct equivalent; requires redesign.
- 🟠 **Rewrite** — equivalent exists but in a different language or engine.
- 🟡 **Behaviour change** — works, but differently; validate.
- 🟢 **Carries over** — no action beyond re-pointing.

---

## 1. T-SQL surface

| Warehouse construct | Lakehouse SQL analytics endpoint | Severity | Replacement |
|---|---|---|---|
| `SELECT` (full DQL) | Supported | 🟢 | — |
| `INSERT` / `UPDATE` / `DELETE` / `MERGE` | **Not supported** | 🔴 | Spark DataFrame writes, Delta `MERGE` in Spark, pipelines, dataflows |
| `CREATE TABLE` / `ALTER TABLE` | **Not supported** | 🔴 | Create Delta tables with Spark; schema managed in the lake |
| `CREATE TABLE AS SELECT` (CTAS) | **Not supported** | 🔴 | `df.write.saveAsTable()` or `CREATE TABLE ... AS SELECT` in Spark SQL |
| `COPY INTO` | **Not supported** | 🔴 | Spark read + write, pipeline Copy activity, or shortcut + `CONVERT TO DELTA` |
| `CREATE VIEW` | Supported | 🟢 | — (but see Direct Lake note below) |
| `CREATE FUNCTION` (scalar / table-valued) | Supported | 🟢 | — |
| `CREATE PROCEDURE` | Supported — but can only read | 🟠 | Read-only reporting procs carry over; any proc that writes must be rewritten in Spark |
| Multi-statement / multi-table transactions | **Not supported** | 🔴 | Redesign for idempotent, single-table-atomic writes; see §5 |
| `IDENTITY` columns | **Not supported** | 🔴 | Surrogate key generation in Spark; see [04-tsql-to-spark-patterns.md](04-tsql-to-spark-patterns.md) |
| `PRIMARY KEY` / `UNIQUE` / `FOREIGN KEY` (non-enforced) | Partially — but see warning | 🟡 | Delta constraints, or enforce in transformation logic |
| Temp tables (`#tmp`) | Not applicable to the write path | 🟠 | Spark temp views, cached DataFrames, or intermediate Delta tables |
| Dynamic SQL in procs | Supported for reads only | 🟠 | Python string-built Spark SQL, or parameterized notebooks |
| `sp_rename`, DDL object management | **Not supported** on autogenerated tables | 🔴 | Managed through Spark DDL on the lake |

> ⚠️ **Foreign key constraint warning.** If you add a foreign key constraint between
> tables in the SQL analytics endpoint, you will no longer be able to make further
> schema changes to those tables (for example, adding new columns). If expected Delta
> columns stop appearing, check for a foreign key constraint blocking metadata updates.

## 2. Table visibility rules

These catch almost every migration at least once.

| Rule | Consequence | Severity |
|---|---|---|
| Only **Delta Parquet** tables are auto-discovered by the SQL analytics endpoint. | Parquet, CSV, ORC, AVRO, and JSON files are **not queryable** through the endpoint. Convert to Delta. | 🔴 |
| Only tables that reference data in the **`Tables/` folder** are exposed. | Anything in `Files/` is invisible to SQL. Move it, or create a table over it. | 🔴 |
| **External Delta tables created by Spark code are not visible** to the endpoint. | Create a **shortcut** in the `Tables` section to surface them. | 🟠 |
| Delta **column mapping by name** is supported; **column mapping by ID is not**. | Tables using ID-based column mapping will not surface correctly. Check before migrating. | 🟠 |
| Columns with Delta types that have no T-SQL equivalent may not appear. | Validate the full column list per table post-migration, not just row counts. | 🟡 |
| Delta tables reached **through shortcuts** are visible and queryable alongside local tables. | Shortcut-based federation works. | 🟢 |
| Legacy Hive tables (Parquet/ORC/AVRO/CSV) are not supported by table maintenance. | Convert to Delta or forgo `OPTIMIZE`/`VACUUM`. | 🟠 |

## 3. Security

Covered in full in [05-security-mapping.md](05-security-mapping.md). Summary:

| Feature | Warehouse | Lakehouse | Severity |
|---|---|---|---|
| Object-level security (`GRANT`/`REVOKE`) | SQL | SQL (delegated mode) or OneLake roles (user identity mode) | 🟡 |
| Row-level security | SQL `CREATE SECURITY POLICY` | SQL security policy (delegated mode) **or** OneLake role RLS rules (user identity mode) | 🟡 |
| Column-level security | `GRANT SELECT` with column list | Same (delegated mode) **or** OneLake role CLS rules (user identity mode) | 🟡 |
| Dynamic Data Masking | `ALTER TABLE ... MASKED WITH ...` | **Delegated mode only.** DDM is **not supported in OneLake security.** | 🟠 |
| Security applies across engines | N/A (SQL only) | SQL-layer rules apply **only** through the endpoint, not through Spark or OneLake | 🔴 |

> 🔴 **The cross-engine gap is the key security risk.** SQL security rules set on the
> SQL analytics endpoint apply *only* when data is accessed through that endpoint. They
> do **not** apply when the same data is read through Spark, notebooks, or OneLake APIs.
> In a Warehouse, SQL *is* the only data path; in a Lakehouse it is one of several.

## 4. Consumption layer

### 4.1 Power BI and Direct Lake

| Condition | Direct Lake on SQL (analytics endpoint) | Direct Lake on OneLake |
|---|---|---|
| SQL RLS defined on the endpoint | Falls back to **DirectQuery**; fails if fallback is disabled | Queries succeed, **SQL RLS is not applied** |
| SQL DDM defined on the endpoint | Falls back to DirectQuery | Not applicable |
| SQL OLS defined on the endpoint | Falls back to DirectQuery | Not applicable |
| Table based on a non-materialized SQL view | Falls back to DirectQuery | **Not supported** — use a materialized lake view instead |
| Composite models (mixing storage modes) | Not supported | Supported |
| Calculated columns / calculated tables over Direct Lake | Not supported | Supported (user context only) |
| DirectQuery fallback available | Yes | **No** (runs `DirectLakeOnly`) |
| Guardrail breach (files, row groups, rows) | Falls back to DirectQuery | — |

Practical implications:

- 🟠 If reports today sit on **Warehouse views** with SQL security, moving to Lakehouse
  will change Direct Lake behaviour. Model this explicitly.
- 🟡 **Framing** still applies: refresh the semantic model after the Delta tables change.
- 🟡 A **single table** breaching a guardrail drops the **entire model** out of Direct
  Lake mode.
- 🟢 Direct Lake on OneLake is the recommended option for new semantic models.

### 4.2 External tools

| Consumer | Impact | Severity |
|---|---|---|
| SSMS / Azure Data Studio / sqlcmd (read) | Works against the endpoint | 🟢 |
| Any tool issuing DML or DDL | **Breaks** | 🔴 |
| ODBC/JDBC write-back applications | **Breaks** | 🔴 |
| Third-party ETL tools writing via T-SQL | **Breaks** — must switch to Spark, pipelines, or OneLake APIs | 🔴 |
| Tools reading Delta directly from OneLake | Works, and improves | 🟢 |

## 5. Transactional and operational semantics

| Warehouse behaviour | Lakehouse behaviour | What to do |
|---|---|---|
| Multi-table ACID transaction wraps a batch load | Each Delta table commits independently | Design for **idempotent reruns** and a **batch/watermark column**; publish a "load complete" marker table consumers check |
| Rollback on failure | No cross-table rollback | Use Delta **time travel** (`RESTORE`) per table, plus an orchestrated restore list |
| System-managed physical layout | **User-managed** | Schedule `OPTIMIZE` and `VACUUM`; see [06-operations-and-performance.md](06-operations-and-performance.md) |
| System-managed cleanup of unreferenced files | **User-managed** | `VACUUM` on a retention policy |
| Warehouse snapshots (point-in-time child item) | **Not available** | Delta time travel, or periodic Delta `CLONE`-style copies |
| Zero-copy clone of tables | **Not available** | Shallow copies via shortcuts, or full copy |
| Immediate read-after-write consistency for SQL readers | **Metadata sync latency** between Spark write and endpoint visibility | Trigger on-demand metadata refresh at the end of each pipeline |

> 🔴 **Metadata sync latency is the most under-estimated operational change.** A Spark
> write is committed to Delta immediately, but the SQL analytics endpoint may not
> surface it for some time. If downstream consumers poll the endpoint, you must add an
> explicit refresh step.

## 6. Ingestion paths

| Path | Warehouse | Lakehouse | Severity |
|---|---|---|---|
| Pipelines (Copy activity) | ✅ | ✅ | 🟢 |
| Dataflows Gen2 | ✅ | ✅ | 🟢 |
| `COPY INTO` (T-SQL) | ✅ | ❌ | 🔴 |
| `INSERT ... SELECT` cross-item | ✅ | ❌ | 🔴 |
| Spark (notebooks, Spark job definitions) | ❌ | ✅ | 🟢 (gain) |
| Shortcuts | ⚠️ limited | ✅ | 🟢 (gain) |
| Eventstreams | ❌ | ✅ | 🟢 (gain) |
| Mirroring targets | — | ✅ | 🟢 (gain) |

## 7. Gap triage worksheet

For each item found by the inventory script, record:

| Object | Type | Severity | Replacement approach | Owner | Effort (d) | Status |
|---|---|---|---|---|---|---|
| `sales.usp_load_fact_order` | Stored proc (writes) | 🔴 | PySpark notebook, Delta MERGE | | | |
| `sales.vw_order_summary` | View (read-only) | 🟢 | Recreate on endpoint | | | |
| `sales.fact_order.order_key` | IDENTITY column | 🔴 | Hash surrogate key | | | |
| `sales.fk_order_customer` | Foreign key | 🟠 | Drop; enforce in transform | | | |
| `rls_policy_region` | Security policy | 🟡 | OneLake role RLS or SQL policy | | | |

Nothing moves to the playbook until every 🔴 has a named replacement approach and an
owner.
